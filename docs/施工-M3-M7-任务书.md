# 施工任务书 · M3–M7 并行线

> 本文件是并行施工的合同。每条线在独立 worktree 上工作，只提交自己的分支；
> 共享文件由 Lead 独占。完成线交付「可点通 + 落库 + 测试 + 截图」四件套。

## 0. 通用规则

1. **工作目录**：每张任务卡指定一个 worktree（如 `<worktree>`）。所有命令的
   `workdir` 都用它。**不要**在 `<repo>` 里改任何文件。
2. **分支**：只在自己的 `feat/wN` 分支提交。不 merge/rebase 到 main，不动别人的分支。
3. **工具链**：
   ```powershell
   $env:PATH="<go-toolchain>\bin;$env:PATH"
   go build ./... ; go test ./... ; go vet ./... ; go tool mygo vet .
   ```
   四项必须全绿才能交付。提交前 `gofmt -w internal`。
4. **提交**：小步提交，消息 `feat(m4): ...`。完成时 `git status --short` 必须干净，
   报告分支、commit hash、文件清单、测试结果、截图路径。
5. **不缩范围**：功能按任务卡全做，不做占位页、不删功能、不改成 WebView。
6. **不改**：`AGENTS.md`、`go.mod`/`go.sum`（确需新依赖先问 Lead）、`main.go`、
   `internal/app/app.go`、`routes.go`、`state.go`、`shell.go`、`bootstrap.go`、
   `backup_settings.go`、`internal/design/tokens.go`、`components.go`、
   `internal/data/sqlite/meta.go`、`user_profiles.go`、`internal/repository/interfaces.go`、
   既有 `internal/domain/*.go`（新类型放新文件）。
7. **不改原始 Flutter 项目**（`<FoodBox-source>` 只读参考）。

## 1. 架构约定

- **页面**：`internal/app/<feature>_views.go` 等由任务卡指定，互相不重叠。
  路由表已注册好，页面函数签名见 `internal/app/routes.go`。
- **状态**：`App` 里已有你的状态块（`a.sched`/`a.sichu`/`a.ai`/`a.nutrition`/`a.feed`/
  `a.prefs`/`a.recipeEdit`）。在自己的文件里给结构体加字段，并在它的 `init()` 里初始化 map。
- **异步**：DB / 网络 / 重计算一律 goroutine，结果用 `a.post(func(){ ... })` 回主线程。
  视图函数里只读快照，不做排序/匹配/解码，不启动 goroutine。
- **DB**：只用 `internal/data/sqlite` 的 `Store` 方法；schema v2 已有全部 10 张表，
  **不要改 schema/migrations**。临时键值（会话、偏好、配额）用
  `Store.MetaGet / MetaSet / MetaGetJSON / MetaSetJSON`（app_meta，不参与备份）。
  多语句写用 `Store.Run(ctx, []Statement{...})` 单事务。
- **服务**：纯逻辑放 `internal/services/<name>`，不 import `ui` 与 `sqlite`。
- **UI kit**：用 `internal/design` 的 `Card / CardPad / SectionHeader / Tile / Chip /
  Pill / Tag / StatCard / EmptyState / KV / Meter / BarChart / ModalPane / FieldLabel /
  HRule / HeaderAction`；颜色只用 `design.Palette` 字段。需要新组件就加到**自己的文件**里，
  不要改 `components.go`。
- **MyGo API**：源码在 `$(go env GOMODCACHE)\github.com\egoist\mygo@v0.7.4\ui\`；
  `api_gen.go` 是全部构造器与方法签名，用 grep 查。测试用 `ui.NewTester`。
- **文案**：中文、克制、不用感叹号、不解释实现细节；空态给出口；按钮动词开头。
- **无障碍**：可点元素用 `ButtonBase/Button/PrimaryButton` 并带 `.Label(...)`；
  列表行给 Label；弹窗按钮文字明确。

**任务**
1. **排程引擎** `schedule.BuildTimeline(recipes []domain.Recipe, steps map[int64][]domain.Step,
   servings map[int64]int, stoveCount int) domain.Timeline`
   - 资源：`step.Resources` 含 `stove` / `board` / `hand` / `waiting`；同资源同刻只排一步。
   - 灶台并行数 = min(锅具件数, 4)，默认 2；案板 2；`hand` 视为可无限并行但受同菜顺序约束。
   - 每道菜步骤保持原顺序；跨菜贪心并行；`waiting` 不占资源。
   - 输出：`Lanes []TimelineLane`（每资源一条，含 Start/End 与步骤）、`TotalMinutes`、
     `SerialMinutes`、`SavedMinutes`。确定性：同输入同输出。
   - 步骤无时长按 1 分钟；无资源按 `hand`。
   - 测试：3 菜样例 golden（写死期望总时长/每条 lane 的步骤顺序）。
2. **备料清单** `schedule.BuildPrep(recipes, items, matcher) []domain.PrepLine`
   - 聚合掌序内每道菜的「必需且非调料」食材；别名归一复用 `internal/services/matcher`。
   - 每行：名称、总需求、单位、来自哪几道菜、在库数量、缺口；颗粒度在库算「有」。
   - 分组：生鲜 / 底料 / 调料（用 `domain.ZoneOf` 与 Kind）。
3. **页面**
   - `/schedule`（重写 `schedulePage`）：待做队列卡片（菜名、份数、时长、移出）、
     统计条、入口按钮「备料清单」「排程时间线」「开始掌序」；空态去菜式。
   - `/schedule/prep`：分组备料表 + 「缺口加入购物清单」（复用 `a.shopExtras` 与
     `a.computeShopping()`）+ 缺口数量汇总。
   - `/schedule/timeline`：时间线视图（用 `ui.Box` + `Draw` 画条，或用 `design.BarChart`
     思路自绘），显示每条 lane 的步骤块与起止分钟；顶部总时长/并行节省；
     灶台数选择（Segmented 1–4）实时重算。
   - `/schedule/run`：歌词流执行全部步骤（`lyricFlow` 复用，lines 为各菜步骤拼接），
     上一步/下一步、键盘左右键、暂停/继续计时、当前步高亮、悬浮计时胶囊
     （`Absolute().Bottom().Right()`）、挂起托盘（显示已挂起的计时）、
     「结算」入口（确认弹窗显示扣减预览）。
4. **会话恢复**：`RunSession`（`domain.RunSession` 已定义）以 JSON 存 app_meta key
   `schedule.run`；`loadScheduleState` 读取；结算/清空后 `ClearRunSession`；
   run 页每步变化与暂停时持久化（goroutine + post）。
5. **结算** `Store.SettleRunFull(ctx, recipeIDs []int64, completedAt time.Time,
   sessionSeconds *int, note string) error`（单事务）
   - `records`：每菜一条，xp=10，session_seconds 写入；
   - **扣库存**：每道菜的必需非调料食材，用别名匹配在库条目：精确数量按用量扣减
     （扣到 <=0 标记 `is_depleted=1`）；颗粒度档位逐档下降
     （plenty→some→low→depleted）；调料不扣。
   - `cook_journal`：按本地日期 upsert，`record_ids` 追加；
   - 清 `schedule_items`；`profiles.xp/total_meals` 累加；失败整事务回滚。
   - 测试：成功路径（库存减少/日记写入/记录写入）、回滚（注入失败）、重复结算不重复扣。
6. 保留原有 `settle()` 行为兼容旧测试（`TestSettleRun` 期望结算后掌序清空、食历有记录）。
   如测试需要调整文案，可改 `shell_test.go` 中你负责的断言。
